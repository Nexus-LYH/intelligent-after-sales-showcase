# identity first implementation slice

Current scope: database-backed PREAUTH/AUTH, explicit capabilities, offline initialization, password change, namespace-scoped account queries and revocation. Endpoints: `GET /api/auth/csrf`, `POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/logout`, `POST /api/auth/password`, `GET /api/identity/users`, `GET /api/identity/users/{id}`, `POST /api/identity/users/{id}/sessions/revoke`.

## Local environment

Use the workspace's `环境工具/Enter-IdentityEnv.ps1` by dot-sourcing it in PowerShell. It supplies Java 21, Maven settings and credentials from outside Git, and verifies/starts the dedicated MySQL instance. This module only accepts explicit `local` profile and loopback; it is not a deployment or gateway bypass configuration.

Run `scripts/Verify-Identity.ps1 -Tests MigrationTest` for the versioned migration. It checks the port (3307), database (`ias_identity_test`) and dedicated datadir before any writes. V1 creates six business tables, V2 retires legacy AUTH credentials once, V3 adds `identity_user_capability`; Flyway has its own schema-history table. Applied migrations are immutable. Runtime startup requires V2/V3 and never creates tables or inserts bootstrap accounts/grants.

After V3, run `scripts/Grant-RevocationPrivileges.ps1` once using the existing private operator configuration. It independently verifies port/schema/datadir and adds only UPDATE on three user-version/timestamp columns and INSERT on operation results. It does not grant capabilities to people. Runtime and normal tests never auto-elevate the database role.

Run `scripts/Verify-Identity.ps1` for the complete test suite. Tests generate only fictitious accounts with randomly generated in-memory passwords and real Argon2id verifiers. No default login credentials are shipped. Tests preserve historical rows; no automatic cleanup is implemented. Browser tests use an installed Chrome executable, a fresh temporary profile and test-only fixture routes. The database outage test verifies port/datadir/schema, invokes the dedicated native client/server without console or inherited output pipes, stops/restarts ONLY the verified 3307 instance and restores it in `finally`.

After migration, use the activated shell and `mvn spring-boot:run` for local startup. JDBC credentials must be injected, never committed or printed. Refer to the approved workspace contract for exact request fields, recovery states and HTTP errors.

## Implementation boundaries

- Authentication values are 32 random bytes; only SHA-256 digests are persisted. CSRF values are independent random synchronizer tokens, controlled in the context table.
- ID-01: first successful me/AUTH csrf atomically replaces the authentication digest while confirming possession. Only a timely, known committed request can send the replacement Cookie. The original Cookie is retired even if post-commit processing fails; no compensating transaction is required. Clients must apply Set-Cookie on these control responses. If the confirmation Cookie response is lost, explicitly log in again after me401. Session ID/attempt/CSRF and absolute expiry do not change, and confirmed sessions never rotate again.
- V2 retires all pre-upgrade AUTH credentials with SYSTEM audit. Stop the old local application before migrating; no mixed-version rollout is supported. Startup requires a successful V2 schema-history entry and never runs this migration automatically. V1 remains immutable.
- The four exposed POST route patterns perform database-bound CSRF checks in the auth domain. Spring Security delegates ONLY these patterns to those checks; its CSRF protection stays enabled elsewhere. There is no global CSRF disable, Basic/form login, framework login user, or HttpSession authentication.
- Signing, verification, confirmation and logout use short READ COMMITTED transactions and the Tenant → User → Session → Attempt lock order. Password work runs outside locks; the signing transaction compares the exact security version used for verification.
- All other routes are denied. Identity type does not grant administrator or business permissions. Department/full RBAC, permission-management APIs, asset binding coordination, internal service authentication/gateway, production TLS and backup recovery remain later slices.
- Restricted accounts can use only current identity-control APIs including confirmed-session password change. Success retires all old sessions and requires explicit login; no in-place upgrade or automatic new session.
- This module has no positive identity cache and no sliding expiration. Expiration/invalid versions are rejected at query time without a cleanup worker.
- The application database role reads identity facts, writes contexts/attempts, inserts operation results, updates only User security_version/row_version/updated_at/password_verifier/must_change_password, and appends audits. It has no DDL, capability writes, other User/Tenant writes or audit/operation update/delete permission. MySQL locking reads use existing LOCK TABLES privilege limited to the approved database; code uses row locks, not LOCK TABLES statements.
- Local single-process rate limiting is bounded and keyed by trusted network origin rather than cookies. It is not a multi-instance global limiter.
- ID-02: the browser test parses exactly one plain-text output#browser-result node, requires data-complete=true, the exact success value and a normal Chrome exit. Script source is excluded. Actual hanging/forced-failure browser cases plus parser negative cases prove RUNNING, failure, incomplete/duplicate/missing nodes and nonzero exit do not pass. Only sanitized result-node values are saved in target/browser-results.json.
- The browser tests intentionally discard login JSON or omit Set-Cookie through a TEST-only transport fixture. This proves the browser recovery branches, not production network reliability or multi-tab late-Cookie intent binding.

Migration constraints, runtime results and remaining verification are linked from the backend advisor's communication record; no separate preparation report is needed.

## Minimal capability and manual revocation slice

- `identity_user_capability` is an explicit per-user allow-list, not a complete role system. No default admin or positive permission is inferred from EMPLOYEE/PLATFORM. The eligible current user also needs the enabled exact capability: `identity.session.revoke` for tenant employees, `identity.platform.session.revoke` for platform identities. CUSTOMER never gains this capability. Scope always comes from the authenticated immutable namespace; platform capability cannot target tenant accounts.
- `me.permissions` and login response permissions are display hints. Every revoke transaction reads current capability facts online. Missing/disabled grant denies; storage failure closes access. Future grant/role changes must lock Tenant then User, change the fact, increment User security_version/row_version (or Tenant epoch for shared roles) and append audit in the same transaction. This slice exposes no grant-management API and does not claim full RBAC/last-admin protection implemented.
- Revoke requires already CONFIRMED/NORMAL AUTH, exact Origin/Referer, bound `X-CSRF-TOKEN`, JSON, and `Idempotency-Key` (1..128 visible ASCII, no spaces). Body contains ONLY reason (5..200 Unicode code points, no control/unpaired-surrogate characters, compared without trim) and expectedSecurityVersion (positive decimal string recommended; integral JSON in signed BIGINT range accepted). IDs/returned versions are decimal strings.
- Tenant lock then sorted actor/target User IDs then Session/Attempt preserves authorization under concurrency, including mutual platform revocation. The target's namespace is checked before any key lookup; current session/capability and CSRF must pass before replay. Actor User locking serializes same-actor keys across all targets; the unique key remains a database backstop. Same key/content returns the original operation before checking stale expected; changed content409, new key with stale version409. Version overflow409.
- A successful transaction advances target versions and inserts operation plus linked before/after audit atomically. It never scans/updates all sessions or deletes history. Self-revocation returns its committed200; later old-session requests401. New login is allowed, and a newly valid authorized actor can replay its own old result. Unknown acknowledgement503 uses the SAME key to recover; no automatic write retry. Local bounded revocation limit uses the configured login-limit count with its own network-origin bucket, returning429.
- V1 digest is SHA-256 of UTF-8 `1\nUSER_SESSIONS_REVOKE\n{targetDecimal}\n{expectedDecimal}\n{reasonUtf8ByteLength}:{reason}`. No credentials are included. Results do not expire automatically.
- `RevocationTest` exercises real HTTP/MySQL, grants, rollback, idempotency and concurrency. Test-only grant changes/SQL fault constraints stay in tests. Its real60s case measures from the observed committed transaction callback and samples at or after60s, not exact equality; cross-service/Range remains unverified.

## Third slice: offline accounts and self-service account controls

The live browser contract is workspace 开发者设计/登录与会话最小契约草案.md section13. Backend explicitly allows http://127.0.0.1:5173; staff uses its same-origin /api proxy to8081. Only local/loopback is supported.

Preparation, using the existing environment, from this module:

1. Dot-source workspace 环境工具/Enter-IdentityEnv.ps1, and build current JAR with mvn -B -ntp -DskipTests package. Building with skipTests is not runtime acceptance.
2. Explicitly execute .\scripts\Grant-AccountPrivileges.ps1 once. It verifies existing3307/schema/datadir, adds only password_verifier/must_change_password column updates to runtime and creates a separate restricted offline initializer operator. Private credentials stay outside Git. It has INSERT/SELECT needed for bootstrap and no UPDATE/DELETE/DDL; it is not the SQL migration/runtime account. Nothing auto-elevates on startup.
3. Explicitly execute .\scripts\Initialize-IdentityAccounts.ps1 -GenerateSecrets. Non-secret plan: bootstrap/local-accounts.json; default random initial password map: C:\ias-local\Develop\IAS-MySQL84\secrets\identity-local-passwords.json, accessible only to current operator/SYSTEM. Script checks ACLs, never prints passwords and never overwrites an existing secret file, even with -GenerateSecrets.
4. Repeat with .\scripts\Initialize-IdentityAccounts.ps1. Same-plan rerun reports ALREADY_EXISTS, never resets passwords/status/force-change/security versions/grants. Changed/disabled existing capabilities or wrong identity cause refusal. No manual business SQL or JUnit fixture needed to create these five usable accounts. All initially enabled and must change their own password. Account names/secret references are in the non-secret plan.
5. Start local identity with mvn spring-boot:run or java -jar .\target\identity-0.0.1-SNAPSHOT.jar from the activated shell. Coordinate3307/8081 ownership in shared records; never overlap outage tests with frontend use.

Initializer script selects com.ias.identity.bootstrap.BootstrapMain explicitly through Boot PropertiesLauncher, passing paths and restricted credentials via environment, no raw password argv. Normal java -jar starts only IdentityApplication, no initialization Runner/controller. CLI independently guards3307/schema/datadir/history, computes Argon2 verifiers outside row locks and serializes offline invocations with a same-connection MySQL advisory lock. One transaction creates missing tenants/accounts/explicit capabilities and SYSTEM audit; error rolls back. No cleanup/reset/takeover path. Failed/unknown acknowledgement prints a generic non-secret code; inspect the plan and rerun the same plan. CLI is test-environment-only, not a production bootstrap promise.

POST /api/auth/password requires confirmed valid AUTH, bound CSRF and source; NORMAL and PASSWORD_CHANGE_REQUIRED can call. Exact three JSON string fields: currentPassword/newPassword/confirmPassword; old1..128 codepoints, new12..128, matching confirmation and different from old, no trim/normalization. Verification/encoding happen outside locks; final Tenant→User→Session transaction rechecks credential/version/state and atomically writes verifier, force-change0, incremented versions and before/after audit.200 only nextAction=LOGIN, clearing current Cookies. No automatic session, password request digest or idempotency store. On503 never assert rollback or retry automatically; clear form values and explicitly log in to check. Error codes in contract13.1.

GET /api/identity/users and /{id} require confirmed NORMAL current capability and namespace, never browser permissions/identity headers. List accepts only keyword/status/page/size, rejects duplicate/unknown inputs, escapes LIKE metacharacters, applies identical namespace/filter predicates to total/items and orders updated_at DESC,id DESC. Page defaults1, max1000000; size20/50/100; status0/1; keyword max100 codepoints. Whitelisted DTO: string IDs/securityVersion, UTC updatedAt, boolean mustChangePassword, named bindingState, null department/minimal tenant summary. No verifier/phone/CSRF/session/token/enterprise facts. Ordinary employees use me, not management endpoints. Detail supplies actual version for revoke; cross-scope404. No user CRUD or grant/password-reset admin APIs.

Tests: scripts/Verify-Identity.ps1 runs the full suite; -Tests 'AccountTest,BootstrapTest' selects new coverage. Test plans are fictional; actual local demo accounts are created separately by CLI and left unchanged for frontend first-login checks. Existing Chrome tests remain login/cookie-recovery coverage, not proof of the new frontend password/list/revoke journey. Shared record/third-batch evidence provide actual results and remaining frontend/independent acceptance.
